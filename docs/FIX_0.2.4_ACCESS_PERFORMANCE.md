# 0.2.4 预览读取性能回归修正

## 已定位的代码变化

0.2.1 为处理 SOAP 701，把授权刷新 Browse 从 count=1 改为 count=50，并在每次重新授权后固定等待 1 秒。0.2.2/0.2.3 的每个未缓存预览仍调用授权准备，可能在读图前重复触发这些操作。0.2.3 的自动清晰 JPG 读取另会增加带宽占用。
用户相机显示“未连接到应用程序”，仅凭照片不能确认是会话过期、读图消耗授权、相机端状态切换还是其他问题。

## 改动

- 缩略图和清晰预览先直接 GET 已有资源；200 不再先做 Browse 或 req_acc。
- 只有明确 HTTP 403 才执行一次授权准备、重试一次原 GET。500、超时等不盲目触发授权。保持同一个 CameraAccessGate，避免与扫描/下载争抢授权。
- 授权刷新恢复 count=1，仅收到结构化 SOAP 701 时回退 count=50。初始目录扫描仍为 count=50，以保留大卡渐进加载行为。
- 重新授权后的播放切换不再一律固定等 1 秒，先尝试 Browse；只有成功切换后仍收到 SOAP 701 才等待并重试。目录扫描的 701 模式恢复仍保留。
- 预览诊断加入 preview-access：direct=200 recovery=0 及首响应耗时；direct=403 recovery=once 记录恢复路径。
- JPG 自动清晰预览与 RAW 快速预览策略保持。若没有相机大预览，完整 JPG 仍会占用传输通道，不能宣称读取 11 MB 与读取小图同速。
- 文件保存队列的恢复策略保持，避免把预览优化直接推广到尚未复测的下载流程。

## 复测

1. 覆盖安装，先滚动查看胶卷缩略图，不打开 JPG。记录前 20 张出现速度与相机是否反复显示未连接。
2. 打开同一张 JPG，观察清晰预览耗时；关闭后滚动是否继续。
3. 复制诊断日志，核对 preview-access direct=200 是否无需恢复；403 是否频繁伴随 req_acc。
4. 与 0.2.0 对比时使用同一相机、同一卡、同一批照片，先断开再连接；不要把已有缓存与首次加载混比。
5. 验证单张 JPG/RAW 下载；再测试断网及重新连接。

未连接真机，不能确认实际提速比例或会话断开的根因。本版未增加未经验证的定时重新授权/保活命令。
历史文档中的“每张图预先刷新 50 项”“授权后固定等一秒”为旧版行为，以本版为准。

日志补充：用户 21:15:31.959—21:15:35.436 的恢复链约 3.48 秒；req_acc_e 的 under_research 到成功约 1.03 秒、playmode 后固定等待 1 秒、50 项 Browse 约 1.216 秒。已成功使用的 SOAP URL 后续收到 403 时立即返回恢复，停止该 URL 的多组格式及备选路径重复尝试；尚未验证过的 URL 保留初次兼容性发现。
