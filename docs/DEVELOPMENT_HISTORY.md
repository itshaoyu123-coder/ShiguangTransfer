# 拾光传输开发历程

这是根据实际版本、机主反馈和调试日志整理的回顾。早期工作尚未使用本仓库逐版提交，因此下述章节不是伪造的 Git 历史，也不能代替完整性能测试。

## 为什么做这个 App

机主使用 Panasonic S5 II（S5M2，也常称 S52），手机是小米 15，反馈环境为 HyperOS 4。256GB 卡中有数千项目，部分使用 JPG+RAW；某次 UPnP 返回总数为 6829 个对象。希望先看到最新照片，扫描剩余目录时仍能预览和导入，不必先等待全卡扫描完成。

项目边界逐渐明确：拾光负责连接、浏览和把原文件带到手机；LUT 编辑希望交给 LUMIX Lab，不在导入工具里另造一套调色器。

## 来源和路线调整

早期 0.1.x 先尝试 Android 外壳和通信接入。真机使用中，连接步骤、预览和下载都暴露问题。随后采用用户提供的 `LumaLink-progressive-source-5.zip`（内部实际为 progressive.3）作为通信与传输基础，再重做界面和继续修复。

因此，本项目不是“只参考了协议、其余完全原创”。协议、UPnP 浏览、下载、队列等大量基于 LumaLink，新增与修改范围有专门记录。保留 Apache-2.0、上游 NOTICE 及第三方声明，是发布工作的一部分。

## 先让照片逐步出现

最初目标是“最新窗口先出现、边扫描边显示”，而不是只做加载动画。

有一个重要区别：UPnP 对象数和用户看到的文件数不是一回事。一个对象可能同时提供 JPG、RAW、缩略图等资源。用文件数代替分页游标会漏图；把全卡资源数混进对象总数，也会误判进度。

渐进扫描沿用并改进输入版本的实现，使用同一相机访问锁协调目录、预览和下载，避免并发重新授权互相干扰。错误发生后保留已出现的照片，而不是清空整个胶卷。

## 预览布局和清晰度

用户截图指出：图片中央的转圈遮挡内容，底部按钮被系统导航区域挤住，JPG 和 RAW 都不够清晰。

0.2.2 调整安全区、按钮和进度显示；0.2.3 区分快速预览与清晰 JPG。列表使用小图，点开 JPG 先显示缓存，再读取相机大预览；没有大预览地址时才用 JPG 原文件解码。RAW 优先快速预览。不能把一张 11MB 原文件的读取时间等同于小缩略图。

清晰度和速度的平衡由机主反复试用反馈决定，没有仅凭成功编译宣称体验已解决。

## 为什么会停住，等相机“未连接”后才继续

这是迭代中最有价值的一组实机问题。

最初日志出现 UPnP HTTP 500；进一步看 SOAP fault 才发现 701（对象/目录状态相关），不能一律按相机忙处理。早期恢复逻辑增加了正常尺寸目录窗口和等待，但也带来回归：预览前重复刷新目录，恢复授权后固定等一秒。

一段用户日志显示，约 3.5 秒耗在目录拒绝、重新授权、相机批准、播放切换和重新读取 50 项目录，图片还没有开始读取。0.2.4 改为先读取图片，明确 403 才恢复，并减少已知地址的格式重试。

但用户仍反馈停顿。后续日志中，多张缩略图连续 HTTP 200，首响应约 0.17—0.55 秒，下一页目录却返回 403，随后再次授权。这个证据说明，不能把所有等待归因于 JPG+RAW 或 Wi-Fi 吞吐量。

0.2.5 同时处理两件事：

- 阻塞的 HttpURLConnection 并不会自动响应协程取消，需要主动关闭连接，并为预览设置较短的无数据等待上限。
- 在共享相机通道内增加低频 getstate 状态查询，尝试维持控制会话；失败只记日志，不定时重新授权。

用户后来反馈扫描和已扫描照片的预览体验明显改善。因为几项改动同时迭代，这不是单独证明“某一条保活命令彻底解决所有固件问题”的实验。

## 分页和锁屏扫描

用户继续使用时，在 3700/6829 附近出现“未返回完整分页”。代码检查发现：正对象数但没有可下载文件的页被当作失败；同名文件被用作去重依据，也可能丢掉不同目录中的照片。

0.2.6 改为按完整资源 URL 去重、按返回对象推进；临时空页在原位置有界重试，不跳过范围、不把失败伪装成全部完成。资源上限也提高，容纳 JPG+RAW 展开的文件数量。

为避免锁屏后只剩 Activity 里的任务，扫描状态改由应用级对象持有，并增加带进度通知的前台服务、必要的 CPU/Wi-Fi 锁。后台取消屏幕缩略图预取，让目录继续；重新进入时为可见照片取图。系统强行停止、进程死亡和换卡后的跨进程续扫仍没有保证。

## 导入后的整理

0.2.7 以后，需求转向完整工作流：

- 导入记录按日分组，删除时明确选择只删记录或同时删除手机文件，相机卡原片不动。
- 预览从直接切换，改为可跟手滑动和吸附动画。
- 胶卷显示拍摄日期并按日筛选，缺失日期明确列为未知。
- 用已有成功导入记录显示“已导入”标记，不增加相机查询。
- 导入记录按需加载手机本地缩略图，限制并发、尺寸与缓存，不向相机再取图。

这些新增功能有相应策略测试和构建检查；不能把尚未回传的实机结果写成用户已逐项确认。

## LUMIX Lab：仍未完成的一项

0.2.7 尝试 ACTION_SEND/VIEW。用户明确反馈：只是进入 Lab 主页，没有打开选中照片的编辑页，因此这条不能算成功。

0.2.8 起只探测公开可调用的 ACTION_EDIT，记录版本和可匹配组件，不猜测私有页面或绕过权限。不支持时明确提供手动图库选择。用户报告的 Lab 版本需要进一步通过安装包或 `lab-handoff` 日志核实；在此之前，不承诺能直达编辑页。

## 开发方式和验证原则

机主提出需求、提供照片截图和日志、进行真机测试；Codex 协助检查 Kotlin/Compose 和通信代码、编译、测试、打包与整理文档。使用 Gradle 命令行构建，并不要求每次都通过 Android Studio 点按钮。

电脑端没有直连相机或手机，也没有完成可运行的模拟器验证。因此区分三种证据：代码实现、自动化检查、用户实机反馈。它们不能互相替代。

当前 0.2.10 本次范围是传输模块 37 项测试及构建/lint。完整输入协议套件仍有 4 项已知失败，保留记录，不通过修改断言来包装“全绿”。

## 下一步

1. 对 S5 II 做固定条件的锁屏、全卡、断网与重连回归，核对是否漏对象/文件。
2. 收集其他松下机型的最小日志和兼容性结果，不直接宣称全系列支持。
3. 核实 Lab 的真实编辑入口；不存在可调用入口时，就把边界保持在导入工具。
4. 配置长期维护的正式签名与可重复发布流程，避免测试密钥和 CI 产物混用。
